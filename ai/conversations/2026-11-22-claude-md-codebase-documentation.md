## Що оформлювати

Оформлюйте архітектурно значущі рішення. Вони зачіпають структуру, нефункціональні характеристики,
залежності, інтерфейси чи спосіб побудови системи. Практичний тест, чи справді воно того варте:

1. **Його дорого або важко скасувати.** Приклад: міграція схеми, формат даних, вибір фреймворку.
2. **Були реальні альтернативи.** Якщо варіант був єдиним, записувати нічого.
3. **Через пів року хтось запитає "чому так?".** Це може бути й ви самі.
4. **Воно наскрізне.** Воно впливає на кілька модулів або шарів.

Не оформлюйте:

- локальні деталі реалізації, які легко змінити;
- те, що вже забезпечують лінтер, Prettier чи commitlint;
- очевидні або безальтернативні речі;
- рішення, які повністю видно з коду та назв.

## 2. Файли налаштувань

Приклад:

```json
{
  "permissions": {
    "allow": [
      "Read(./src/**)",
      "Bash(npm run lint)",
      "Bash(npm run build)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "ask": ["Bash(git push:*)", "Bash(git commit:*)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}
```

- `allow` виконується без запиту.
- `ask` завжди питає.
- `deny` забороняє повністю, і воно має пріоритет над `allow`.

**1. Обмежити `TResult` спільним типом id (я б рекомендував).**

```ts
export type Id = string; // за бажанням branded: string & { readonly __brand: 'Id' }

export abstract class CommandHandler<TCommand, TResult extends Id | void = void> {
  abstract handle(command: TCommand): Promise<TResult>;
}
```

Тоді команда може повертати лише id або нічого, а `Promise<BackupListItem[]>` у команді вже не

мусили б мати щось, що ідентифікувати: наприклад, id відновленого бекапу чи id операції. Зараз
такого немає, тож доведеться вигадувати.
